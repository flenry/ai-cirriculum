## Strategic Assessment

The research choices are directionally good, but the board should **not treat them as settled yet**. There is a major alignment problem: the **research handover conflicts with the original brief/PLAN/PRD assumptions** on key APIs. If you proceed to implementation without reconciling that drift, you risk building the wrong product cleanly.

### Highest-priority board concern
There are two competing specs in circulation:

- **Research handover says:** Open-Meteo, Firebase HN API, GitHub REST, Wikipedia Action API
- **Original brief / current PRD baseline say:** OpenWeatherMap, HN Algolia, Wikipedia REST summary

That is not cosmetic. It changes:
- auth requirements
- response shapes
- implementation complexity
- UX quality of the generated brief
- test fixtures
- env var contract

My recommendation: **board resolves API canon now before build starts.**

## Option Ratings

Scale: **1 low / poor → 5 high / strong**

## 1) Weather API

### Option A — Open-Meteo
**Feasibility:** 5/5  
**Risk:** 2/5  
**Strategic fit:** 5/5  

**Why it wins**
- No API key, lower setup friction
- Simpler onboarding for a personal cron tool
- Good enough for “daily brief” use case
- Better fit with “minimal personal utility” than commercial weather APIs

**Risks / assumptions to challenge**
- Research cites `current_weather=true`; verify it still matches the intended production response contract
- If the product wants “city-first” UX, Open-Meteo works best with coordinates, so geocoding may become a hidden requirement
- Weather codes are less human-friendly than descriptive text unless you map them yourself

**Board take**
Best default if the product optimizes for **ease, reliability, and low-friction setup**.

---

### Option B — OpenWeatherMap
**Feasibility:** 4/5  
**Risk:** 3/5  
**Strategic fit:** 3/5  

**Pros**
- City-name input is straightforward
- Human-readable weather descriptions out of the box
- Well-known API

**Cons**
- API key and account creation add friction
- Strictly weaker strategic fit for a personal automation tool where simplicity matters
- Research already ruled it out; keeping it would mean knowingly choosing more overhead

**Board take**
Viable, but strategically inferior unless the product explicitly prioritizes **city-name configuration over frictionless setup**.

**Recommendation:** Choose **Open-Meteo**, but decide whether config is:
- `WEATHER_LAT` / `WEATHER_LON` only, or
- city input plus geocoding fallback

Do not leave that ambiguous.

## 2) Hacker News source

### Option A — Firebase official HN API
**Feasibility:** 4/5  
**Risk:** 3/5  
**Strategic fit:** 4/5  

**Pros**
- Official source
- Stable and canonical
- Strong long-term correctness

**Cons**
- Requires multiple requests: one for IDs, then N item fetches
- More implementation complexity
- More failure points and slower runs unless batched carefully

**Strategic risk**
For a cron-based personal brief, “official” may matter less than “simple and robust.” Officialness is not free.

---

### Option B — HN Algolia API
**Feasibility:** 5/5  
**Risk:** 2/5  
**Strategic fit:** 4/5  

**Pros**
- Single query gives enriched front-page data
- Simpler implementation and testing
- Faster and cleaner for v1 brief generation

**Cons**
- Not the canonical source
- Search/indexing lag could create slight divergence from official top stories

**Board take**
If the goal is **best v1 execution with minimum complexity**, Algolia is the stronger delivery choice.  
If the goal is **source purity**, Firebase wins.

**Recommendation:** For v1, I would actually favor **Algolia** unless “official API only” is a product principle.  
The current research picked Firebase, but I’d challenge that assumption: you may be trading simplicity away for purity you don’t need.

## 5) Scheduler

### Option A — node-cron inside app
**Feasibility:** 5/5  
**Risk:** 4/5  
**Strategic fit:** 3/5  

**Pros**
- Cross-platform
- Simple for a Node app
- Good developer experience

**Cons**
- Misses runs if the process is down
- Makes reliability depend on a long-running process
- Weak for “daily automation” unless deployment/runtime is explicitly managed

**Board stress test**
What happens if:
- laptop is asleep at scheduled time?
- process crashes overnight?
- machine reboots?
- DST shifts?

If those cases matter, node-cron alone is not enough.

---

### Option B — system cron / external scheduler
**Feasibility:** 3/5  
**Risk:** 2/5  
**Strategic fit:** 5/5  

**Pros**
- Better operational reliability
- Better fit for a true daily job

**Cons**
- Less portable
- Slightly more setup/documentation burden

**Board take**
Research rejected system cron for complexity, which is fair for implementation.  
But strategically, the board should not confuse **easier to code** with **best operating model**.

**Recommendation:**  
For v1:
- implement a **single-run CLI command**
- document scheduling via **system cron** as preferred in production/personal use
- keep `node-cron` optional if you want an always-on mode

That gives both portability and reliability.

## Key Risks the Board Should Surface

### 1. Spec drift risk — highest
Research, PLAN, and existing PRD assumptions do not match.  
This is the biggest delivery risk because it creates false confidence.

**Board action:** lock one canonical API set before build.

---

### 2. Scheduler reliability risk
A cron feature that silently misses runs undermines the product’s core promise.

**Board action:** require a single-run CLI and document external scheduling as preferred.

---

### 3. Wikipedia UX risk
Action API may technically work while producing a weaker brief.

**Board action:** require title + summary + URL, not just random page title.

---

### 4. HN complexity creep
Firebase official API is “correct” but may be a poor v1 trade if it requires many network calls.

**Board action:** explicitly decide whether “officialness” is worth added implementation cost.

---

### 5. GitHub notification usability risk
Raw API payloads don’t automatically map to readable, clickable user output.

**Board action:** require normalization into repo name, subject type, human URL, updated time.

---

### 6. Partial-failure policy ambiguity
If one API fails, what exactly is stored? What gets rendered? What counts as a successful run?

**Board action:** define success as “brief generated with best-effort sections,” and persist partial briefs with per-section status.

- **Weather:** Open-Meteo

- **GitHub:** REST Notifications API
- **Wikipedia:** REST random summary endpoint
- **Storage:** SQLite + Drizzle
- **Scheduling:** single-run CLI + documented system cron; `node-cron` optional, not foundational
- **Rendering:** Chalk + inline HTML
